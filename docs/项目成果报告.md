# 极修匠企业微信侧边栏门店经营数据中台项目成果报告

生成日期：2026-06-23  
适用场景：简历项目经历、个人网站项目详情、项目交接说明  
公开安全口径：本文只描述工程架构、接口类型、数据处理链路和项目成果，不包含企业微信 Secret、抖音 Cookie、凡科授权密钥、数据库密码、服务器登录凭据等敏感信息。

## 一、项目一句话概括

本项目是为极修匠业务搭建的“企业微信外部群侧边栏门店经营数据看板”，员工在企业微信客户群侧边栏打开自建应用后，系统会自动识别当前群聊对应的门店，并展示该门店的上翻收益、直播时长、视频发布、门店评分、核销金额、核销券数、抖音已核销订单、凡科电池/电芯订单等经营指标。

项目本质上不是单纯的前端页面，而是一套连接企业微信、抖音来客、抖音开放平台、凡科商城和本地 MySQL 的门店数据中台。

## 二、项目背景与业务价值

极修匠门店运营需要在企业微信外部客户群里快速判断门店当前经营状态。原本数据分散在多个系统中：

1. 抖音来客后台能看到门店上翻收益、直播、视频、核销等数据。
2. 抖音开放平台能查询订单和券码核销状态，但需要按接口同步。
3. 凡科商城保存电池、电芯类订单，需要按手机号和门店绑定关系再做聚合。
4. 企业微信群名和真实门店之间存在重名、评级前缀、多门店群、超级门店等复杂匹配情况。

项目解决的核心问题：

1. 员工不用在多个后台之间切换，直接在企业微信群侧边栏查看门店经营状态。
2. 通过自动群名识别减少人工搜索门店的操作成本。
3. 每天定时同步并落库，避免侧边栏实时依赖第三方后台的稳定性。
4. 把多源数据统一成门店维度，供后续 AI 客服和运营工具复用。

## 四、技术栈

后端：

1. FastAPI：提供企业微信、侧边栏、抖音、凡科、同步状态等 API。
2. SQLAlchemy + MySQL：保存门店经营数据、同步日志、凡科订单明细、抖音官方订单。
3. APScheduler：每天自动同步门店数据、凡科订单、抖音官方订单。
4. httpx：异步调用企业微信、抖音、凡科等外部接口。
5. openpyxl / xlrd：解析门店映射表、电话表、凡科分类表和导出的 Excel 数据。
6. cryptography：处理企业微信回调加解密。
7. Playwright：在部分接口直连不稳定时模拟浏览器导出或拦截数据作为兜底方案。

前端：

1. Vue 3 + Vite：实现企业微信侧边栏页面。
2. Axios：调用后端 API。
3. 企业微信 JS-SDK：获取当前外部群和侧边栏上下文。

部署：

1. 腾讯云 Ubuntu 服务器。
2. Nginx 反向代理和 HTTPS 证书。
3. Uvicorn systemd 服务运行 FastAPI。
4. 前端构建产物由 Nginx 提供静态访问。

## 六、企业微信自建应用构建流程

### 1. 创建企业微信自建应用

在企业微信管理后台创建自建应用，配置应用名称、Logo、可见范围，并记录以下配置项：

1. 企业 ID，也就是 CorpID。
2. 应用 AgentID。
3. 应用 Secret。
4. 客户联系相关 Secret，如果需要读取外部客户群，需要配置客户联系权限。
5. 回调 Token 和 EncodingAESKey。

这些信息只应写入服务端环境变量，不能写入前端源码，也不能放到公开简历或网站里。

### 2. 配置可信域名和 HTTPS

企业微信 JS-SDK 只能在可信域名下正常工作，所以需要：

1. 准备一个 HTTPS 域名，例如项目中使用 `jxjfix.com`。
2. 在服务器配置 Nginx，把域名代理到 FastAPI 和前端静态文件。
3. 在企业微信后台设置 JS-SDK 可信域名。
4. 按企业微信要求上传域名验证文件到站点根路径，确保 `https://域名/验证文件.txt` 能被访问。

### 3. 配置侧边栏入口

在企业微信自建应用或客户联系能力里配置应用入口 URL：

```text
https://jxjfix.com/
```

侧边栏打开后，前端页面会使用企业微信 JS-SDK 读取当前上下文。

### 4. 配置回调地址

项目后端提供两个企业微信回调入口：

```text
GET/POST https://jxjfix.com/callback/command
GET/POST https://jxjfix.com/callback/data
```

回调用于企业微信验证和接收事件。后端会按企业微信规则校验签名，并使用 Token、EncodingAESKey 解密回调内容。

### 5. 前端初始化 JS-SDK

前端核心文件：

```text
frontend/src/utils/wecom.js
frontend/src/views/Sidebar.vue
```

前端流程：

1. 获取当前页面 URL。
2. 调用后端 `/api/v1/jssdk/config` 获取 `wx.config` 签名。
3. 调用后端 `/api/v1/jssdk/agent-config` 获取 `wx.agentConfig` 签名。
4. 注册企业微信 JS API：
   - `getCurExternalChat`
   - `getContext`
   - `sendChatMessage`
5. 调用 `wx.invoke('getCurExternalChat')` 获取当前外部群 `chatId`。

### 6. 后端生成 JS-SDK 签名

核心文件：

```text
backend/app/routers/jssdk.py
backend/app/services/token_manager.py
```

后端签名逻辑：

1. 使用企业微信 Secret 获取 `access_token`。
2. 使用 `access_token` 获取 `jsapi_ticket`。
3. 使用 `agent_ticket` 生成应用级 `agentConfig` 签名。
4. 按企业微信规则拼接：

```text
jsapi_ticket=xxx&noncestr=xxx&timestamp=xxx&url=xxx
```

5. 对拼接字符串做 SHA1，返回给前端。

### 7. 获取当前群信息

核心文件：

```text
backend/app/routers/wecom.py
backend/app/services/wecom_client.py
```

前端拿到 `chatId` 后调用：

```text
GET /api/v1/wecom/group/info
```

后端优先调用企业微信客户群接口：

```text
/externalcontact/groupchat/get
```

如果客户群接口失败，再降级尝试应用群聊接口：

```text
/appchat/get
```

返回群名称后，前端再调用：

```text
POST /api/v1/wecom/match-store
```

后端根据群名匹配门店并返回侧边栏数据。

## 七、群名匹配门店的业务算法

核心文件：

```text
backend/app/routers/wecom.py
backend/app/services/store_group_mapping.py
测试文件/重复门店名_poi_id对照表_补全群名.xlsx
```

匹配顺序：

1. 优先读取 Excel 对照表，做“群名 -> poi_id”的精确映射。
2. 对群名进行标准化：
   - 中文括号统一成英文括号。
   - 去除空格和不可见字符。
   - 去除 `A`、`B+`、`C-` 等评级前缀。
   - 清理“超级门店”等业务前缀。
3. 支持一个群对应多个门店：
   - 从括号中提取门店关键词。
   - 支持 `、`、`,`、`，`、空格等分隔符。
   - 返回 `stores` 数组，前端可切换查看。
4. Excel 没命中时，再用关键词匹配 `store_performance.poi_name`。
5. 对包含“极修匠”的群名做品牌保护，优先选择门店名中也包含“极修匠”的记录。
6. 如果 Excel 中的 `poi_id` 当前没有同步到经营数据表，则按 `poi_name` 兜底查找，但展示时保留映射里的 `poi_id`。

这部分是项目最重要的业务工程能力之一，因为真实企业微信群名并不总是严格等于门店名称。

## 九、抖音来客后台数据获取链路

### 1. `life.douyin.com` 数据

核心文件：

```text
backend/app/services/gmv_data_client.py
```

接口用途：

1. 上翻收益。
2. 直播时长。
3. 视频数量。
4. 门店 `poi_id` 和 `poi_name`。

调用地址：

```text
https://life.douyin.com/life/homed_view/gmv_data/store_operating_list
```

关键请求参数：

```text
root_life_account_id：抖音来客根账号 ID
start_day：统计开始日期
end_day：统计结束日期
yesterday：统计截止日
page：页码
page_size：每页数量，当前使用 50
```

关键请求头：

```text
cookie：抖音来客后台登录 Cookie
x-secsdk-csrf-token：CSRF Token
rpc-persist-life-merchant-role：商户角色标识
```

处理逻辑：

1. 每天同步“当月 1 日到昨天”的门店经营数据。
2. 如果今天是每月 1 日，则回退同步上个月完整数据，避免新月份当天没有昨天数据导致看板空白。
3. 分页获取门店列表，清洗金额、直播时长和视频数量。
4. 把 `poi_id`、`poi_name`、`gmv_yuan`、`live_duration_seconds`、`video_count` 写入 `store_performance`。

### 2. `www.life-data.cn` 数据

核心文件：

```text
backend/app/services/life_data_client.py
backend/app/services/life_data_playwright.py
```

接口用途：

1. 新发布门店关联视频数 `video_cnt_1d`。
2. 门店评分 `poi_score`。
3. 核销金额。
4. 核销券数。

主要接口：

```text
https://www.life-data.cn/api/dito/query
```

关键请求头：

```text
cookie：life-data 登录 Cookie
life-account-id：生活服务账号 ID
root-life-account-id：根账号 ID
x-csrftoken：可选 CSRF Token
```

项目中遇到的问题和解决方式：

1. 该接口返回的不是简单列表，而是深层页面布局结构，门店数据藏在 `poiRanking` 等节点里，所以代码实现了递归解析。
2. 该接口分页不是传统的 `page/page_size`，而是 `offset/limit`，项目中调整为正确分页方式。
3. 直连接口有时会返回空结果或少页数据，所以同步任务会做数量校验。
4. 当 API 结果不稳定时，优先走页面导出的 Excel，再用 `openpyxl` 解析。
5. 如果直接 API 或导出都受限，再使用 Playwright 启动浏览器，模拟真实访问并拦截 `/api/dito/query` 或下载 Excel。

最终策略：

1. 先尝试稳定的 Excel 导出方式。
2. 解析 Excel 得到门店概览、评分、视频和核销数据。
3. 校验返回数量，避免第三方接口异常导致本地数据被空结果覆盖。
4. 失败时再走分页接口或 Playwright 兜底。

## 十、抖音开放平台官方订单同步链路

核心文件：

```text
backend/app/services/douyin_token_manager.py
backend/app/services/douyin_order_sync.py
backend/app/routers/douyin.py
```

调用地址：

```text
https://open.douyin.com/goodlife/v1/trade/order/query/
```

认证方式：

1. 使用抖音开放平台 Client Key / Client Secret 获取 client token。
2. 请求头携带 `access-token`。
3. 请求头携带 `Rpc-Transit-Life-Account` 指定生活服务账号。

同步方式：

1. 定时任务每天 12:20 执行。
2. 同步最近 48 小时订单。
3. 按 1 小时窗口拆分，降低单次接口返回过大和分页不完整风险。
4. 每页最大 200 条，最多 200 页。
5. 入库时按 `(account_id, order_id)` 唯一键做 upsert。

订单解析：

1. 订单金额接口单位是分，入库时同时保存分和元。
2. 解析 `certificate` 数组，统计券码数量和已核销券码数量。
3. `order_status = 201` 且券码 `item_status = 100` 时按已核销处理。
4. 从 `poi_id` 或 `intention_poi_id` 关联门店。
5. 根据商品名称和 SKU 关键词把订单分类为：
   - 苹果电池。
   - 安卓电池。
   - 苹果电芯。
   - 安卓电芯。
6. 原始响应只保存脱敏后的 JSON，不保存明文手机号、券码、open_id 等敏感信息。

侧边栏聚合：

1. 读取近 30 天已核销订单。
2. 按 `poi_id` / `intention_poi_id` 匹配当前门店。
3. 按商品大类聚合电池和电芯订单数量。
4. 展示到侧边栏的“抖音已核销订单”区域。

最近一次核查数据例子：

```text
核查日期：2026-06-23
抖音官方订单总量：182715
覆盖门店数：4827
当天同步记录数：35924
当天新增订单：23706
当天更新订单：35914
当天按核销时间统计的已核销订单：4129
```

这些数据说明项目已从单纯门店看板扩展为可沉淀大量订单明细的数据平台。

## 十一、凡科订单同步链路

核心文件：

```text
backend/app/services/fanke_client.py
backend/app/services/fanke_token_storage.py
backend/app/services/fanke_order_sync.py
backend/app/routers/fanke.py
backend/app/services/store_phone_mapping.py
```

接口域名：

```text
https://waybill.api.jz.fkw.com
```

OAuth 流程：

1. 后端生成凡科授权链接。
2. 用户打开授权链接并同意授权。
3. 凡科回调：

```text
GET /api/v1/fanke/oauth/callback
```

4. 后端用授权码换取 `access_token` 和 `refresh_token`。
5. Token 独立保存到本地授权文件，过期后自动刷新。

主要接口：

```text
/api/oauth/getAuthCode
/api/oauth/getAccessToken
/api/oauth/refreshAccessToken
/api/product/getList
/api/order/getList
/api/order/getMerchantOrderList
```

同步内容：

1. 普通商品订单。
2. 入驻商户订单。
3. 订单商品明细。
4. 买家手机号和收货电话。
5. 商品编码、商品标题、SKU、单价、数量、明细金额。

处理逻辑：

1. 每天同步近 30 天凡科订单。
2. 同时拉取普通订单和商户订单。
3. 对跨来源重复订单做去重，重复时优先保留商户订单版本。
4. 将订单商品明细拆成 `fanke_buyer_order_items` 表的一行一商品。
5. 通过商品编码或标题匹配分类表：
   - `苹果成品.xls`
   - `聚信电芯.xls`
   - `安卓电池.xls`
   - `安卓电芯.xls`
6. 只统计有效订单状态：
   - `wait_seller_ship`
   - `shipped`
   - `finished`
7. 使用 `门店记录表.xlsx` 的门店电话映射，标准化后和订单手机号、订单电话匹配。
8. 如果电话匹配不上，侧边栏展示“电话不一致”，提醒运营检查门店电话数据。

侧边栏聚合：

1. 通过当前门店 `poi_id` 找到门店电话。
2. 用电话匹配凡科订单明细。
3. 按电池、电芯两类汇总订单金额和订单数量。
4. 展示凡科电池/电芯总金额、订单数和同步时间。

## 十三、定时任务和稳定性设计

核心文件：

```text
backend/app/services/scheduler.py
```

当前定时任务：

| 时间 | 任务 | 作用 |
|---|---|---|
| 11:20 | `sync_store_performance` | 同步抖音来客和 life-data 门店经营数据 |
| 11:50 | `sync_fanke_recent_orders` | 同步近 30 天凡科订单 |
| 12:20 | `sync_douyin_official_recent_orders` | 同步近 48 小时抖音官方订单 |

稳定性措施：

1. 门店经营数据同步时，如果第三方接口返回空数据，直接中止，避免把线上数据覆盖成空。
2. 删除旧数据和插入新数据放在同一事务内，失败时回滚。
3. 同步日志记录成功、失败、记录数和错误信息，便于排查。
4. 应用启动时会检查数据是否更新到昨天，必要时触发补同步。
5. 第三方 Cookie、Token 和账号 ID 从配置文件或环境变量读取，避免硬编码在业务代码里。
6. 抖音官方订单按小时窗口同步，降低分页和接口波动风险。
7. 凡科订单按近 30 天重建明细，保证侧边栏查询口径稳定。

## 十五、项目难点和解决方案

### 1. 企业微信群和门店无法一一严格对应

问题：

真实群名存在评级前缀、括号、多门店、重名门店、品牌混写、超级门店等情况。

解决：

1. 建立 Excel 精确映射表。
2. 统一做群名标准化。
3. 支持括号关键词拆分和多门店返回。
4. 增加品牌保护和 `poi_id` 优先级。
5. 对历史问题门店持续追加映射，避免新建重复代码文件。

### 2. 第三方后台不是标准开放 API

问题：

部分抖音来客后台数据需要依赖 Cookie，life-data 返回结构复杂，分页规则和常见 API 不一致。

解决：

1. 通过 httpx 模拟后台请求。
2. 针对深层布局结构写递归解析器。
3. 改正分页参数为 `offset/limit`。
4. API 不稳定时切换到 Excel 导出。
5. 必要时使用 Playwright 模拟浏览器兜底。

### 3. 订单数据口径复杂

问题：

抖音订单需要判断券码是否核销，凡科订单需要按手机号匹配门店，还要区分电池和电芯。

解决：

1. 抖音订单解析券码数组，按已核销状态聚合。
2. 凡科订单拆到商品明细级别。
3. 建立商品分类表，按编码和标题匹配。
4. 建立门店电话映射，标准化手机号后聚合。

### 4. 生产数据不能被空结果覆盖

问题：

第三方接口偶发空响应，如果直接覆盖数据库，会导致侧边栏全量无数据。

解决：

1. 对接口结果数量做校验。
2. 空结果中止同步。
3. 事务内删除和插入。
4. 保留同步日志和错误信息。
